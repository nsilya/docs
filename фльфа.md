## 🔷 Блок 2: Техническая подготовка (только под вакансию)

### ❗ Обязательно знать:
| Тема | Что именно | Где практиковать |
|------|------------|------------------|
| **Iceberg** | - Time travel (`TIMESTAMP AS OF`) <br> - Schema evolution (`ALTER TABLE ... ADD COLUMN`) <br> - ACID vs Hive | Локальный Spark 3.5 + Iceberg (Docker) |
| **Spark** | - Чтение/запись Parquet/Iceberg <br> - DataFrame API (PySpark) | `pyspark --packages org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.4.3` |
| **Airflow** | - `PythonOperator`, `BashOperator` <br> - Идемпотентность DAG’ов <br> - Генерация DAG’ов по шаблону | Пилотный DAG: миграция одной таблицы |
| **SQL** | - Оконные функции (`ROW_NUMBER()`, `LAG`) <br> - CTE, JOIN, UNION <br> - Валидация: `COUNT`, `SUM`, `DISTINCT` | LeetCode, Northwind |
| **Миграция** | - Сравнение Hive vs Iceberg <br> - Валидация данных (checksum, row count) <br> - Документирование бизнес-логики | README.md в GitHub |

### 🚫 Не трать время на:
- Kafka/CDC (только базовое понимание),
- Hadoop/HDFS (ты уходишь *от* него),
- ML, streaming, сложные архитектуры.

## 🔷 Блок 3: Ответы на ключевые вопросы

### Q1: «У вас нет опыта с Hive/Iceberg. Почему мы должны взять вас?»
> «Я не работал с Hive в продакшене, но глубоко изучил его ограничения: отсутствие ACID, сложность schema evolution, невозможность time travel.  
> Iceberg решает эти проблемы — и я уже тестирую его в локальном Spark 3.5.  
> Моя сила — не в знании конкретного инструмента, а в **умении анализировать legacy-системы и строить надёжные миграции**. Это то, что нужно для вашей задачи».

### Q2: «Как вы будете мигрировать витрину с 100 таблиц?»
> «Поэтапно:  
> 1. **Анализ**: метаданные, зависимости, объёмы.  
> 2. **Классификация**: fact/dim/aggregate.  
> 3. **Автоматизация**: генератор DAG’ов по шаблону.  
> 4. **Валидация**: row count, checksum, агрегаты.  
> 5. **Документация**: бизнес-правила, схема, результаты.  
> Главное — **инкрементальный подход**, без big bang».

### Q3: «Как боретесь с изменениями в источниках?»
> «Через **метаданный контроль**:  
> - Сравниваю схему перед каждой выгрузкой,  
> - При расхождении — останавливаю DAG с алертом,  
> - Использую **динамическую генерацию SQL** по текущей схеме.  
> Это позволяет избежать поломок при изменении источника».

### Q4: «Как работаете с документацией?»
> «Документация — часть продукта. В моих проектах:  
> - Каждый DAG — с README (что делает, как запустить),  
> - Каждая миграция — с описанием бизнес-логики,  
> - Изменения схемы — фиксируются в Confluence.  
> Это позволяет новому инженеру **воспроизвести логику без меня**».
